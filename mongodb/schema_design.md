# Проектирование документной модели MongoDB

## Основные сущности

В системе используются три основные сущности:

- пользователь
- водитель
- поездка

Для них созданы три коллекции:

- `users`
- `drivers`
- `rides`

Такой вариант выбран потому, что эти сущности имеют самостоятельный жизненный
цикл. Пользователь может существовать без водительского профиля и без поездок.
Водительский профиль создается отдельно от учетной записи пользователя. Поездка
является отдельным заказом, который связывает пассажира и водителя.

## Общая схема коллекций

```text
┌──────────────────────────┐       ┌──────────────────────────┐       ┌────────────────────────────┐
│          users           │       │         drivers          │       │           rides            │
├──────────────────────────┤       ├──────────────────────────┤       ├────────────────────────────┤
│ _id                 PK   │       │ _id                 PK   │       │ _id                   PK   │
│ id                  UQ   │       │ id                  UQ   │       │ id                    UQ   │
│ login               UQ   │◄──┐   │ user_login          REF  │──► users.login              │
│ password_hash            │   └───│ login               UQ   │◄──┐   │ passenger_login       REF  │──► users.login
│ first_name               │       │ car { ... }         EMB  │   └───│ driver_login          REF  │──► drivers.login
│ last_name                │       │ car_class                │       │ route { from, to }    EMB  │
│ email                    │       │ status                   │       │ car_class                  │
│ role                     │       │ rating                   │       │ status                     │
│ rating                   │       │ shifts [ ... ]      EMB  │       │ price                      │
│ created_at               │       └──────────────────────────┘       │ created_at                 │
│ profile { ... }     EMB  │                                          │ events [ ... ]        EMB  │
│ saved_places [ ... ] EMB │                                          └────────────────────────────┘
│ payment_methods [ ] EMB  │
└──────────────────────────┘
```

Обозначения:

- `PK` - первичный идентификатор документа. В MongoDB это поле `_id`, которое
  создается автоматически.
- `UQ` - уникальное бизнес-поле. Для таких полей создается unique index.
- `REF` - логическая ссылка на документ из другой коллекции.
- `EMB` - вложенный документ или массив, который хранится внутри родительского
  документа.

Важно: MongoDB не создает внешние ключи как PostgreSQL. Поэтому связи
`drivers.user_login`, `rides.passenger_login` и `rides.driver_login` являются
логическими ссылками. Их целостность поддерживается приложением и индексами.

## Коллекция `users`

Коллекция `users` хранит учетные записи пользователей. Пользователь может быть
обычным пассажиром или иметь роль водителя.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  id: "u-1",
  login: "ivan",
  password_hash: "4317ddd8c6efe1208decf85c36bee03bd55d85aa7fe58be11a01256f36bb87cd",
  first_name: "Ivan",
  last_name: "Ivanov",
  email: "ivan@example.com",
  role: "passenger",
  rating: 4.8,
  created_at: ISODate("2026-01-10T10:00:00Z"),
  profile: {
    phone: "+79990000001",
    locale: "ru-RU"
  },
  saved_places: [
    { title: "Home", lat: 55.7558, lon: 37.6173 },
    { title: "Work", lat: 55.7522, lon: 37.6156 }
  ],
  payment_methods: ["card", "cash"]
}
```

### Описание полей

| Поле | Тип | Обязательное | Назначение |
|---|---|---|---|
| `_id` | `ObjectId` | да | Системный идентификатор MongoDB |
| `id` | `String` | да | Бизнес-идентификатор пользователя |
| `login` | `String` | да | Уникальный логин для входа и поиска |
| `password_hash` | `String` | да | Хэш пароля |
| `first_name` | `String` | да | Имя пользователя |
| `last_name` | `String` | да | Фамилия пользователя |
| `email` | `String` | нет | Email пользователя |
| `role` | `String` | да | Роль: `passenger` или `driver` |
| `rating` | `Number` | нет | Средний рейтинг пользователя |
| `created_at` | `Date` | да | Дата создания аккаунта |
| `profile` | `Object` | нет | Вложенный профиль пользователя |
| `profile.phone` | `String` | нет | Телефон |
| `profile.locale` | `String` | нет | Локаль интерфейса |
| `saved_places` | `Array<Object>` | нет | Сохраненные адреса пользователя |
| `payment_methods` | `Array<String>` | нет | Способы оплаты |

### Почему `profile` хранится как embedded document

Профиль пользователя является частью аккаунта. Телефон и локаль почти всегда
нужны вместе с основными данными пользователя, например при отображении профиля
или проверке контактных данных. У профиля нет самостоятельного жизненного цикла:
он не существует отдельно от пользователя.

Поэтому `profile` хранится внутри документа `users`, а не в отдельной коллекции.
Это уменьшает количество запросов к базе: приложение получает аккаунт и профиль
одним чтением.

### Почему `saved_places` хранится как embedded array

Сохраненные адреса принадлежат конкретному пользователю. Они не используются
другими пользователями и не требуют самостоятельного поиска как отдельная
сущность. При открытии профиля или создании поездки приложению удобно получить
эти адреса вместе с пользователем.

Поэтому `saved_places` хранится массивом внутри `users`.

### Почему `payment_methods` хранится как embedded array

Способы оплаты также относятся только к одному пользователю. В текущей модели
это простые значения, например `card`, `cash`, `bonus`. Отдельная коллекция
усложнила бы модель без практической пользы.

Поэтому `payment_methods` хранится массивом строк внутри документа пользователя.

## Коллекция `drivers`

Коллекция `drivers` хранит водительские профили. Водительский профиль связан с
пользовательской учетной записью, но хранится отдельно, потому что содержит
специфичные для водителя данные: автомобиль, статус доступности, рейтинг и смены.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  id: "d-1",
  user_login: "petr",
  login: "petr",
  car: {
    model: "Hyundai Solaris",
    number: "A123AA777",
    class: "economy",
    year: 2021
  },
  car_class: "economy",
  status: "FREE",
  rating: 4.9,
  shifts: [
    {
      started_at: ISODate("2026-05-01T08:00:00Z"),
      finished_at: ISODate("2026-05-01T18:00:00Z")
    }
  ]
}
```

### Описание полей

| Поле | Тип | Обязательное | Назначение |
|---|---|---|---|
| `_id` | `ObjectId` | да | Системный идентификатор MongoDB |
| `id` | `String` | да | Бизнес-идентификатор водителя |
| `user_login` | `String` | да | Reference на `users.login` |
| `login` | `String` | да | Логин водителя, используемый API |
| `car` | `Object` | да | Данные текущего автомобиля |
| `car.model` | `String` | да | Модель автомобиля |
| `car.number` | `String` | да | Номер автомобиля |
| `car.class` | `String` | да | Класс автомобиля |
| `car.year` | `Number` | да | Год выпуска автомобиля |
| `car_class` | `String` | да | Дублированный класс авто для быстрой фильтрации |
| `status` | `String` | да | Статус водителя: `FREE`, `BUSY`, `OFFLINE` |
| `rating` | `Number` | нет | Рейтинг водителя |
| `shifts` | `Array<Object>` | нет | История рабочих смен |

### Почему водитель вынесен в отдельную коллекцию

Водительский профиль не встроен в `users`, потому что не каждый пользователь
является водителем. Если хранить водительские поля прямо в `users`, документы
пассажиров содержали бы много пустых или неиспользуемых полей.

Кроме того, с водителями выполняются отдельные частые запросы:

- найти свободных водителей;
- найти водителей нужного класса автомобиля;
- обновить статус водителя;
- получить профиль водителя по логину.

Поэтому `drivers` является отдельной коллекцией.

### Почему `user_login` является reference

Поле `user_login` ссылается на `users.login`. Это показывает, что водительский
профиль принадлежит конкретному пользовательскому аккаунту.

Связь выбрана как reference, потому что:

- пользователь и водительский профиль имеют разные наборы данных;
- пользователь может существовать до создания водительского профиля;
- данные пользователя используются не только в контексте водителя;
- водительский профиль часто ищется отдельно от пользовательского профиля.

### Почему `car` хранится как embedded document

Текущий автомобиль является частью водительского профиля. При поиске водителя
обычно сразу нужны модель, номер и класс машины. У объекта `car` нет отдельного
жизненного цикла в рамках этой лабораторной работы.

Поэтому `car` хранится внутри документа `drivers`.

### Почему `shifts` хранится как embedded array

Смены относятся к конкретному водителю. В тестовой модели это небольшая история
рабочих интервалов, которая может быть получена вместе с профилем водителя.

Поэтому `shifts` хранится массивом внутри `drivers`. Если бы история смен была
очень большой и требовала отдельной аналитики, ее можно было бы вынести в
отдельную коллекцию, но для текущей задачи embedded-модель проще и удобнее.

## Коллекция `rides`

Коллекция `rides` хранит заказы такси: активные поездки и историю завершенных
поездок.

### Структура документа

```javascript
{
  _id: ObjectId("..."),
  id: "r-1",
  passenger_login: "ivan",
  driver_login: "petr",
  route: {
    from: { lat: 55.7558, lon: 37.6173 },
    to: { lat: 55.7522, lon: 37.6156 }
  },
  car_class: "economy",
  status: "COMPLETED",
  price: NumberDecimal("350.00"),
  created_at: ISODate("2026-05-20T10:00:00Z"),
  events: [
    { type: "created", at: ISODate("2026-05-20T10:00:00Z") },
    { type: "accepted", by: "petr", at: ISODate("2026-05-20T10:02:00Z") },
    { type: "completed", by: "petr", at: ISODate("2026-05-20T10:25:00Z") }
  ]
}
```

### Описание полей

| Поле | Тип | Обязательное | Назначение |
|---|---|---|---|
| `_id` | `ObjectId` | да | Системный идентификатор MongoDB |
| `id` | `String` | да | Бизнес-идентификатор поездки |
| `passenger_login` | `String` | да | Reference на `users.login` |
| `driver_login` | `String` / `null` | нет | Reference на `drivers.login`; `null`, пока поездка не принята |
| `route` | `Object` | да | Маршрут поездки |
| `route.from` | `Object` | да | Координаты начальной точки |
| `route.from.lat` | `Number` | да | Широта начальной точки |
| `route.from.lon` | `Number` | да | Долгота начальной точки |
| `route.to` | `Object` | да | Координаты конечной точки |
| `route.to.lat` | `Number` | да | Широта конечной точки |
| `route.to.lon` | `Number` | да | Долгота конечной точки |
| `car_class` | `String` | да | Требуемый класс автомобиля |
| `status` | `String` | да | Статус поездки |
| `price` | `Decimal128` | да | Стоимость поездки |
| `created_at` | `Date` | да | Дата создания заказа |
| `events` | `Array<Object>` | нет | История событий поездки |

### Почему `passenger_login` является reference

Пассажир хранится в коллекции `users`, а поездки хранятся отдельно в `rides`.
Один пассажир может создать много поездок. Если встроить все поездки в документ
пользователя, документ пользователя со временем стал бы слишком большим, а
работать с активными заказами было бы неудобно.

Поэтому в `rides` хранится ссылка `passenger_login` на `users.login`.

### Почему `driver_login` является reference

Один водитель может выполнить много поездок. Водитель также является отдельной
сущностью со своим статусом, автомобилем и рейтингом. Если хранить поездки
внутри водителя, документ водителя быстро рос бы, а поиск активных поездок по
статусу стал бы менее удобным.

Поэтому в поездке хранится ссылка `driver_login` на `drivers.login`. Для новой
поездки это поле может быть `null`, потому что водитель назначается не сразу.

### Почему `route` хранится как embedded document

Маршрут принадлежит только одной поездке и не используется независимо от нее.
При просмотре заказа приложению сразу нужны координаты начальной и конечной
точки. Отдельная коллекция для маршрутов привела бы к лишним запросам.

Поэтому `route` встроен в документ `rides`.

### Почему `events` хранится как embedded array

События описывают жизненный цикл конкретной поездки:

- создание заказа;
- принятие заказа водителем;
- завершение поездки;
- отмена поездки.

Эти события нужны при просмотре истории одной поездки и не являются
самостоятельной сущностью. Поэтому они хранятся массивом внутри документа
`rides`.

## Итоговое обоснование embedded/reference

| Связь или поле | Решение | Обоснование |
|---|---|---|
| `users.profile` | embedded | Профиль принадлежит одному пользователю и читается вместе с ним |
| `users.saved_places` | embedded | Адреса принадлежат одному пользователю и не нужны как отдельная коллекция |
| `users.payment_methods` | embedded | Способы оплаты являются настройкой конкретного пользователя |
| `drivers.user_login -> users.login` | reference | Водительский профиль связан с отдельной учетной записью пользователя |
| `drivers.car` | embedded | Автомобиль является частью водительского профиля |
| `drivers.shifts` | embedded | Смены относятся к одному водителю и в текущей модели имеют небольшой объем |
| `rides.passenger_login -> users.login` | reference | Один пользователь может иметь много поездок |
| `rides.driver_login -> drivers.login` | reference | Один водитель может выполнить много поездок |
| `rides.route` | embedded | Маршрут принадлежит одной поездке |
| `rides.events` | embedded | События описывают жизненный цикл одной поездки |

## Индексы

Для частых запросов создаются индексы:

| Индекс | Тип | Для чего нужен |
|---|---|---|
| `users.login` | unique | Авторизация и поиск пользователя по логину |
| `users.first_name, users.last_name` | compound | Поиск пользователей по имени и фамилии |
| `drivers.login` | unique | Поиск водителя по логину |
| `drivers.status, drivers.car_class` | compound | Поиск свободных водителей нужного класса |
| `rides.status, rides.created_at` | compound | Список активных заказов с сортировкой по дате |
| `rides.passenger_login, rides.created_at` | compound | История поездок пассажира |
| `rides.driver_login, rides.created_at` | compound | История поездок водителя |

Индексы создаются в файле `validation.js`.
