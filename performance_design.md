# Стратегия кеширования и ограничения частоты запросов


## Сводка решений

| Область              | Решение                                                                  |
|----------------------|--------------------------------------------------------------------------|
| Кеш-хранилище        | Redis 7 (один экземпляр на кластер)                                      |
| Клиентская библиотека| `libhiredis` (синхронный API, обёрнут в Userver-компонент `redis-client`)|
| Стратегия кеша       | Cache-Aside (lazy loading) с явной инвалидацией при записи               |
| TTL                  | 60 с для профиля пользователя; 30 с для профиля водителя                 |
| Алгоритм rate limit  | Fixed Window Counter (`INCR` + `EXPIRE`)                                 |
| Лимит на `/v1/login` | 5 запросов / 60 с / IP в production-режиме, 30 / 60 с в режиме тестов    |
| Поведение при сбое   | Cache-miss → запрос в БД. Rate-limit → fail-open (разрешать запрос).     |

## 1. Анализ производительности

### 1.1. Горячие точки (hot paths)

| Endpoint                          | Сервис         | Частотность вызова                                                                                |
|-----------------------------------|----------------|---------------------------------------------------------------------------------------------------|
| `GET /v1/users?login=…`           | user-service   | Запрашивается клиентом при просмотре профиля и в большинстве UI-сценариев                         |
| `GET /internal/users/{login}`     | user-service   | Вызывается ride-service на каждом запросе истории поездок `GET /v1/users/{login}/rides`           |
| `GET /internal/drivers/{login}`   | driver-service | Вызывается ride-service на каждом `RideAccept`, `RideComplete`, `GET /v1/rides?status=active`     |
| `POST /v1/login`                  | user-service   | Вызывается при каждой клиентской сессии и при попытках подбора пароля                             |

### 1.2. Медленные операции

| Операция                                          | Ожидаемая латентность | Причина                                  |
|---------------------------------------------------|-----------------------|------------------------------------------|
| Запрос к PostgreSQL / MongoDB по docker-сети      | 1–3 мс                | Сетевой RTT + парсинг ответа             |
| Межсервисный HTTP-вызов через `userver::clients`  | 2–5 мс                | TLS handshake (отключён в lab) + RTT     |
| Полнотекстовый поиск `SearchByNameMask` (ILIKE)   | 10–80 мс              | Sequential scan без trigram-индекса      |
| Хеширование пароля (`SHA-256` + pepper)           | < 0.1 мс              | Локальная CPU-операция                   |

### 1.3. Нефункциональные требования

| Требование                                                                | Целевое значение                |
|---------------------------------------------------------------------------|---------------------------------|
| p99 latency на горячих GET-endpoint'ах при умеренной нагрузке             | < 50 мс                         |
| Доля запросов к БД, обслуженных кешем (cache hit rate)                    | > 80%                           |
| Защита `/v1/login` от перебора пароля                                     | ≤ 5 попыток/мин/IP (production) |
| Поведение при недоступности Redis                                         | Деградация без отказа сервиса   |

## 2. Стратегия кеширования

### 2.1. Кешируемые данные

| Кеш-ключ                          | Содержимое      | Источник правды                  | TTL  |
|-----------------------------------|-----------------|----------------------------------|------|
| `cache:user:by_login:<login>`     | JSON `User`     | таблица `users` в Postgres/Mongo | 60 с |
| `cache:driver:by_login:<login>`   | JSON `Driver`   | таблица `drivers` в Postgres     | 30 с |

Пространство имён `cache:` отделено от пространства имён `rl:` (rate limiting), что исключает взаимные коллизии при инвалидации.

### 2.2. Выбор стратегии

| Стратегия      | Решение     |
|----------------|-------------|
| Cache-Aside    | **Выбрана** |
| Read-Through   | Отклонена   |
| Write-Through  | Отклонена   |
| Write-Back     | Отклонена   |

Обоснование:

- **Cache-Aside** — минимальное связывание handler'а и кеша; полный контроль над инвалидацией; работает при недоступности Redis без изменений в коде handler'ов.
- **Read-Through** — требует прослойки между handler'ом и репозиторием; усложняет код handler'ов ради экономии нескольких строк, без выигрыша по производительности.
- **Write-Through** — дополнительный round-trip к Redis на каждую запись; в проекте writes редки, выигрыша по согласованности нет.
- **Write-Back** — теряется строгая согласованность для критических операций (логин, статус водителя). Недопустимо для авторизации.

Применённый алгоритм Cache-Aside:

1. handler выполняет `GET <cache-key>` в Redis.
2. При попадании в кеш (`HIT`) — handler возвращает значение клиенту с заголовком `X-Cache: HIT`.
3. При промахе (`MISS`) — handler обращается к репозиторию, формирует JSON-ответ, пишет `SET <cache-key> <value> EX <ttl>` и возвращает результат с заголовком `X-Cache: MISS`.
4. При операциях изменения (`POST`, `UPDATE`) — handler выполняет `DEL <cache-key>` сразу после успешного обновления источника правды.

### 2.3. TTL и обоснование

| Сущность | TTL  | Обоснование                                                                                       |
|----------|------|---------------------------------------------------------------------------------------------------|
| User     | 60 с | Профиль изменяется редко (email/имя). Длинный TTL приемлем; safety-net на случай пропуска `DEL`.   |
| Driver   | 30 с | Статус (`FREE`/`BUSY`/`OFFLINE`) меняется при каждом accept/complete. Короткий TTL ограничивает stale-окно. |

### 2.4. Инвалидация кеша

- Успешный `POST /v1/users` → `DEL cache:user:by_login:<login>`.
- Успешный `POST /v1/drivers` → `DEL cache:driver:by_login:<login>`.
- Успешный `POST /internal/drivers/{login}/status` → `DEL cache:driver:by_login:<login>`.

Операция `DEL` идемпотентна и выполняется даже если ключ отсутствует.

### 2.5. Поведение при недоступности Redis

- `RedisClient::Get(key)` возвращает `std::nullopt`.
- `RedisClient::SetEx(...)` и `Del(...)` логируют предупреждение и завершаются без ошибки.
- Запрос обслуживается из репозитория (БД).
- Сервис не отказывает клиенту; деградация ограничена ростом нагрузки на БД.

## 3. Стратегия rate limiting

### 3.1. Защищаемые endpoint'ы

`POST /v1/login` — единственный endpoint, для которого введено ограничение частоты запросов:

- Угроза: перебор пароля (brute-force, credential stuffing).
- Лимит в production-режиме: 5 запросов / 60 с / IP.
- Лимит в lab-режиме (значение по умолчанию `LOGIN_RATE_LIMIT`): 30 запросов / 60 с / IP.
- Идентификатор клиента: значение заголовка `X-Real-IP`, проставляемое api-gateway (nginx).
- Ключ в Redis: `rl:login:<X-Real-IP>:<window_start>`, где `window_start` — Unix-timestamp начала текущего окна.

Остальные endpoint'ы защищены требованием Bearer-токена; ресурсоёмкость отдельного запроса ниже стоимости хеширования пароля, поэтому отдельный лимит не введён.

### 3.2. Выбор алгоритма

| Алгоритм               | Решение   |
|------------------------|-----------|
| Fixed Window Counter   | **Выбран**|
| Sliding Window Log     | Отклонён  |
| Sliding Window Counter | Отклонён  |
| Token Bucket           | Отклонён  |
| Leaky Bucket           | Отклонён  |

Обоснование:

- **Fixed Window Counter** — реализуется двумя командами Redis (`INCR` + `EXPIRE`). Состояние лимита прозрачно отображается в три заголовка `X-RateLimit-*`. Допустимый недостаток: в худшем случае клиент может совершить до 2×limit запросов на стыке окон; для защиты `/v1/login` этого недостаточно для успешного подбора пароля.
- **Sliding Window Log** — точный, но требует операций над сортированными множествами и удаления устаревших записей; избыточен для одного защищаемого endpoint'а.
- **Sliding Window Counter** — компромисс между точностью и сложностью, но требует двух ключей и взвешивания на границе окна.
- **Token Bucket** — допускает контролируемый burst, что нежелательно при защите от перебора пароля.
- **Leaky Bucket** — поведение аналогично Token Bucket; реализация поверх Redis требует Lua-скрипта.

### 3.3. Параметры реализации

- Размер окна: 60 секунд.
- Источник идентификатора клиента: заголовок `X-Real-IP`; запасной вариант — адрес TCP-партнёра.
- Источник значения лимита: переменная окружения `LOGIN_RATE_LIMIT`; значение по умолчанию — 30.
- Используемые команды Redis: `INCR <key>` (при каждом запросе) и `EXPIRE <key> 60` (только при первом инкременте окна).

### 3.4. Ответ при превышении лимита

- HTTP-код: `429 Too Many Requests`.
- Тело: `{"error": "rate_limited", "message": "too many login attempts, retry later"}`.
- Заголовок `X-RateLimit-Limit` — заданный лимит запросов в окне.
- Заголовок `X-RateLimit-Remaining` — `max(0, limit − использовано)`.
- Заголовок `X-RateLimit-Reset` — оставшиеся секунды до сброса окна.

Заголовки `X-RateLimit-*` проставляются на любом ответе endpoint'а (200, 400, 401, 429), что позволяет клиенту отслеживать остаток лимита без отдельного запроса.

### 3.5. Поведение при недоступности Redis

- `RedisClient::Incr` возвращает 0 (нейтральное значение).
- `RateLimiter::Acquire` интерпретирует 0 как «лимит не превышен» и возвращает `allowed = true`.
- Логика fail-open: выбор между избыточной строгостью при сбое Redis и потерей возможности логина у всех клиентов одновременно сделан в пользу доступности сервиса.
- Атакующий по-прежнему ограничен пропускной способностью сети и CPU user-service.

## 4. Метрики и мониторинг

### 4.1. Ключевые метрики

- **Cache hit rate** — отношение количества ответов с заголовком `X-Cache: HIT` к общему числу запросов на endpoint. Источник: access-log nginx.
- **Latency p50 / p99 (cached)** — распределение времени ответа отдельно для `HIT` и `MISS`. Источник: метрики Userver.
- **Rate-limit reject rate** — отношение количества ответов `429` к общему числу запросов на `/v1/login`. Источник: access-log nginx.
- **Redis availability** — результат `redis-cli PING` и число ошибок в логах компонента `redis-client`. Источник: docker healthcheck.

### 4.2. Целевые значения

| Endpoint                          | Целевой hit rate | Ожидаемое снижение нагрузки на БД (rps=100) |
|-----------------------------------|------------------|---------------------------------------------|
| `GET /v1/users?login=…`           | ≥ 90 %           | До ≈ 1.7 rps к БД                           |
| `GET /internal/users/{login}`     | ≥ 90 %           | До ≈ 1.7 rps к БД                           |
| `GET /internal/drivers/{login}`   | ≥ 80 %           | До ≈ 3.3 rps к БД                           |

### 4.3. Способ измерения эффективности

1. Запустить нагрузочный тест (например `wrk -t4 -c100 -d60s`) на cached endpoint с фиксированным значением `login` при выключенном кеше.
2. Зафиксировать p50, p99 и throughput.
3. Запустить идентичный тест с включённым кешем.
4. Сравнить показатели. Ожидаемое снижение p50 — порядок величины (с единиц миллисекунд до сотен микросекунд).

## 5. Ожидаемый эффект

| Аспект                                       | Без оптимизаций                            | С реализованной стратегией                               |
|----------------------------------------------|--------------------------------------------|----------------------------------------------------------|
| Нагрузка на БД на горячих чтениях            | 100 % запросов попадают в БД               | 10–20 % при стабильной нагрузке                          |
| Latency p50 `GET /internal/drivers/{login}`  | ≈ 3 мс (RTT БД + парсинг)                  | ≈ 0.4 мс (Redis HIT)                                     |
| Стабильность хвоста latency                  | Зависит от пиков нагрузки на БД            | Чувствительна только к RTT Redis                         |
| Устойчивость к перебору пароля               | Ограничена только производительностью CPU  | Жёсткое ограничение N запросов/мин/IP                    |
| Поведение при сбое Redis                     | Не применимо (Redis не используется)       | Деградация без отказа: кеш-промах + fail-open rate limit |
